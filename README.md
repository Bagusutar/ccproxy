# ccproxy

本机 HTTP 代理，将 Claude Code 的各个模型位分别路由到不同的上游 API。

Claude Code 只能配置一个 API 地址。该地址一经确定，主模型、内置模型别名与后台任务
默认使用同一供应商，无法分别指定上游。

ccproxy 在本机监听一个端口，依据请求中的模型名将流量路由至对应上游。
Claude Code 无需改动，其配置中仍是单一地址。

单文件可执行程序，无需安装，放在任意位置。后台代理以数据目录中的服务映像运行，
启动器可在代理运行期间替换或删除。

## 快速开始

### Windows

双击 `ccproxy.exe` 打开控制面板：

1. 添加上游，填写地址与凭证，点击「获取模型列表」，再点击「连通性测试」
2. 在「模型分配」中为各模型位指定上游与模型
3. 点击「保存并应用」

控制面板随后可以关闭，后台代理常驻。默认端口 `15722`。

### Linux / WSL

```bash
chmod +x ccproxy
./ccproxy
#   ccproxy 配置界面: http://127.0.0.1:xxxxx/?k=...
```

浏览器打开输出的地址（其中的 `k` 参数是必需的，缺少时接口返回 `forbidden`），
其余步骤与 Windows 相同。开机自启使用 systemd user unit，不需要 root。

若该环境的出站流量经过代理，需要将本地地址排除在外：

```bash
export NO_PROXY=localhost,127.0.0.1,::1
```

## 模型路由

Claude Code 将模型划分为若干位置，ccproxy 支持为每个位置单独指定上游与模型：

| 模型位 | 用途 |
| --- | --- |
| 主模型 | 会话本身 |
| haiku | 后台任务，以及委派规则显式选择的 Haiku 请求 |
| opus / sonnet / fable | `/model` 和委派规则显式选择的对应模型请求 |

路由依据是请求体中的 `model` 字段，而非请求路径。采用控制面板提供的委派规则后，
内置 Agent 显式选择的模型名同样按此规则路由。各上游的模型目录合并为一份对外提供，
`/model` 选择器可列出全部可用模型。

## 协议转换

Claude Code 仅发送 Anthropic Messages 格式的请求。ccproxy 支持三种协议并按需转换：

- Anthropic Messages
- OpenAI Chat Completions
- OpenAI Responses

协议支持情况按「模型 × 端点」逐项探测，不按上游统一判定；同一供应商的不同模型，
可用协议可能不同。探测结果保存于本地配置，请求时查表：原生支持的路径直接透传，
响应字节不做修改，仅在需要转换时进入转换层。

反向亦可用：仅支持 OpenAI 接口的客户端指向同一地址，即可访问 Anthropic 的模型。
前提是请求由本机发出——将请求交由自家服务器转发的客户端无法接入，
本代理只监听 `127.0.0.1`。

## 故障处理

故障处理由代理完成，客户端可见行为如下：

- **请求发出后无响应** — 默认 95 秒未收到响应头时自动重发；客户端尚未收到数据时才会重发。
- **响应流中断** — 默认 60 秒无数据时结束当前响应，使客户端可以重新请求。
- **上游临时错误** — 收到 408、500、502、503、504、520、524 或 529 时自动重发，最多三次。
- **结构化输出不可用** — 上游不支持或未遵守 schema 时，代理使用工具调用维持结构化结果。
- **无法统计 token** — 上游没有 `count_tokens` 端点时，代理使用本地估算，结果可能偏高。
- **上游拒绝模型** — 对 403 等权限错误保留上游状态，并返回可识别的原因说明。

出站连接遵循 `HTTP_PROXY` / `HTTPS_PROXY` / `NO_PROXY`。

## 用量统计

控制面板提供两种统计口径，均可按日期范围查询，并按配置单价估算费用：

- **代理流量** — 统计所有经过 ccproxy 的请求，按上游和模型累计输入、缓存写入、缓存读取、输出 token。
- **Claude Code 会话** — 读取本机 Claude Code 会话记录，统计主线与 Agent 的用量。

费用估算按每百万 token 的输入、缓存写入、缓存读取和输出单价分别计算；内置常见模型单价，
可在控制面板覆盖。人民币单价按固定汇率折算为美元。无单价的模型仍显示 token 用量，但不产生费用估算。

Claude Code 会话用量会自动去重，避免同一条消息被重复计入。

## 磁盘足迹

```
%LOCALAPPDATA%\ccproxy\        Windows
~/.config/ccproxy/             Linux
├── ccproxy-service.exe        后台代理运行的服务映像
├── config.json                含真实凭证
├── ccproxy.log
├── status.json
└── usage.json
```

- Claude Code 自己的配置目录只被读取。唯一的写入是 `settings.json`，
  仅改写受管字段，其余键的内容与顺序原样保留，首次接管前备份一次原文件。
- 写入 `settings.json` 的凭证是占位符，真实密钥只存在于 `config.json` 与代理进程内存中。
  该文件的访问权限继承自上级目录。
- 启动器所在位置由用户决定，程序不记录该路径，因此不会被任何持久化配置引用。

**服务映像为何是单独一份**：Windows 不允许删除或覆盖已加载的映像。
若守护进程直接运行用户手上那个 exe，它在代理运行期间就无法移动、替换或删除。

## 卸载

控制面板中点击「卸载并还原」：

1. `settings.json` 按安装前的原值逐键回滚，原本不存在的键予以删除而非置空
2. 停止后台代理，取消开机自启
3. 删除数据目录下的全部文件，含服务映像，目录本身一并删除

启动器不在清理范围内，自行删除即可。

## 构建

```bash
# Windows
GOOS=windows GOARCH=amd64 go build -trimpath -ldflags="-H windowsgui -s -w" -o ccproxy.exe .

# Linux（静态链接，不依赖 glibc 版本）
CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build -trimpath -ldflags="-s -w" -o ccproxy .
```

`-trimpath` 不可省：不加它，Go 会把构建机的源码路径嵌进二进制。

`rsrc_windows_amd64.syso` 是 Windows 的图标资源，由 `tools/mkicon` 生成，
需要保留在源码树中，否则构建出的 exe 没有图标。

## 限制

- 图形界面依赖 WebView2（Windows 11 自带）；Linux 上退化为本地网页界面。
- 代理只监听 `127.0.0.1`，本机以外无法访问。将其暴露到公网需要自行实现，
  本程序不提供该能力——进程内存中持有真实凭证，且不校验入站身份。
- Agent 之间不做协调，多个 Agent 可能重复读取同一文件。
- 按模型位分流的收益随任务规模增长；三步以内、仅涉及一两个已知文件的任务，
  委派开销大于收益。
